# Contributing Guidelines

There are many ways to contribute to EVE Frontier Dapp Index, including
participating in GitHub Discussions, opening issues, improving documentation,
and submitting pull requests.

## Discussions and support

Use GitHub Discussions for builder questions, listing ideas, metadata proposals,
Sui registry feedback, Walrus publishing questions, and general community
coordination.

Discussions are also the preferred place to contribute early feedback before an
idea becomes an issue or pull request. Start there when you want to propose a
new metadata field, category, smart assembly facet, registry rule, approval
model, or builder workflow.

You can also help other users in the community solve their issues in the
[Discord]: https://discord.com/invite/evefrontier

## Opening an issue

You can [open an issue] to suggest a feature or report a bug.

Before opening an issue, search through the existing open and closed issues, and
consider posting a comment in one of those instead.

When requesting a new feature, include as many details as you can, especially
around the builder, player, or registry use cases that motivate it. Features are
prioritized according to the impact they may have on the Frontier ecosystem, so
we appreciate information showing that the impact could be high.

[open an issue]: https://github.com/evefrontier/dapp-index/issues

## Submitting a pull request

If you would like to contribute code or documentation, you may do so by forking
the repository and submitting a pull request.

### Branch and commit standards

- Branch from `main`. Name branches per
  [Conventional Branch 1.1.0](https://conventionalbranch.org/).
- Write commit messages per
  [Conventional Commits 1.0.0](https://www.conventionalcommits.org/en/v1.0.0/).
- Repo-specific rules: `AGENTS.md` → Git and GitHub conventions.

Example:

```text
feat/builder-publish-readiness
  feat(builder): add publish readiness blockers
  test(builder): cover slug ownership publish action
```

### Pull request description

When you open a PR, GitHub offers two templates under
`.github/PULL_REQUEST_TEMPLATE/`:

| Template | Use when |
| --- | --- |
| **code.md** | Default — site, Move, schema, Walrus, or any behavior change |
| **docs.md** | Docs-only or agent-config changes (minimal fields) |

**Required for every PR:** Summary and Verification.

**Add when relevant — otherwise delete the section:**

| Section | When to include |
| --- | --- |
| **Related work** | Stacked PRs, issues, or follow-ups |
| **Scope** | Code template — one line naming the surface(s) touched |
| **Reviewer notes** | Manual testing, trust/wallet/release impact, or UI screenshots |

Verification is usually a single line (`bun run site:test` pass) rather than
checking six boxes. For docs-only PRs, the **docs** template defaults to
`Not run — docs-only.`

Do **not** add tool attribution ("Made with Cursor", "Generated by Codex", etc.).
PR descriptions should read like maintainer-written notes, not agent marketing.

Make sure to run the relevant linters and tests before submitting your pull
request. Changes to the Sui Move registry, Walrus metadata flow, or builder
metadata model may require extra maintainer review.

Please keep the scope of your PR small. It's better to open multiple small PRs
than one huge PR, as smaller PRs are easier to review and merge.

When opening the pull request, read the template carefully and follow all
applicable sections. Expect a review and feedback from the maintainers
afterwards.
